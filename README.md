# Tally

A tap-and-swipe macro tracker — log a meal without typing a word. Native iOS (SwiftUI), backed
by Supabase (Postgres). Started life as an HTML/JS prototype (see `prototype/` once it's ported
over) to work out the UX before writing any Swift.

## Status

Core loop works end-to-end, verified live on Simulator: Home → pick a meal → pick a food → set
quantity/unit/variant → log it → Home's calorie ring, macro bars, and meal list update from a
real Supabase read. `FoodMathTests` pins the unit-conversion math to values already verified
against both the prototype and this app. Settings → Daily Targets and Water Goal are also wired
up and verified end-to-end (edit → save → Home picks up the change from Supabase). Home also
supports swiping between days (with the same slide/fade transition as the prototype) and
tapping the header to jump back to today — each day's data is fetched fresh from Supabase.
Water editing (tap the running total to correct/reset it, separate from the +Add flow) and
weight tracking (Settings → Weight, one value per day) are both wired up and verified. The
food picker's Usual/A-Z sort toggle works (Usual = by last_used_at, maintained by the DB
trigger), and custom foods can be created inline from the food picker ("Create Custom Food"),
tagged for whichever meal you were adding to, with no oz/g toggle since they're serving-based.
Searching in the food picker now spans the whole catalog regardless of the meal filter, and
Settings → Manage Foods lists every food (searchable) with a Customize screen to rename it,
change its icon (a 70-emoji picker grid), or adjust its base macros. Meal templates round out
the list — save any meal's current items by name from Home, then re-log the whole thing in one
tap from the food picker's Templates section; templates store references, not frozen macros, so
they always reflect current food data.

**Every feature from the original prototype's scope is now ported and verified.** What's left is
bigger-picture, not individual features: real-device testing beyond Simulator, HealthKit,
real auth (still single hardcoded user — see the RLS note below), and eventually the paid
Apple Developer account for TestFlight/App Store distribution.

## Stack

- **Swift / SwiftUI**, no paid Apple Developer account yet — runs on Simulator, and on your own
  device via free provisioning (7-day expiry; just re-run from Xcode to refresh).
- **Supabase (Postgres)** as the source of truth for everything — food catalog, logs, water,
  weight, templates. No auth yet: every row is scoped to one hardcoded `user_id` (see
  `supabase/schema.sql`). Add real accounts before this app is ever shared with anyone else.
- **XcodeGen** generates the `.xcodeproj` from `project.yml`, which is the file to hand-edit —
  the generated project itself isn't committed (see Setup below).

## Setup (fresh clone)

```bash
brew install xcodegen                      # if you don't already have it
cp .env.example .env                       # then fill in your Supabase project's values
./scripts/sync-secrets.sh                  # writes Config/Secrets.xcconfig from .env
xcodegen generate                          # writes Tally.xcodeproj from project.yml
open Tally.xcodeproj
```

Run the two Supabase SQL files once against a fresh project (SQL Editor in the Supabase
dashboard, in order): `supabase/schema.sql`, then `supabase/seed.sql`.

Whenever you edit `project.yml` or `.env`, re-run the relevant command above — neither the
generated project nor the generated secrets file is committed, so they need regenerating after
a clone or a config change.

```
  sync-secrets.sh         — .env → Config/Secrets.xcconfig
```

## Data model notes worth remembering

- Calories are never stored — always `protein_g*4 + carbs_g*4 + fat_g*9`, computed the same way
  everywhere (SQL, Swift) so numbers can't drift between layers.
- Food/variant macro fields are **per one native unit** (e.g. per egg, per slice, per oz for
  oz-native foods), not per gram — convert through `grams_per_unit` first. Item-mode foods
  (Oreos, Chips Ahoy) are the exception: their macros are per labeled serving
  (`items_per_serving` cookies), not per single item.
- `log_entries` snapshots macros at log time, so editing a food's catalog values later never
  rewrites history. `meal_templates` deliberately does the opposite — it stores food
  *references*, so re-applying a template always uses current data.
- RLS currently allows the `anon` key full access to every table (no auth exists yet to scope
  policies against). Fine for a personal, undistributed app; must be tightened before sharing
  this with anyone else.
